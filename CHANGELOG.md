# Changelog

## [Unreleased](https://github.com/dichovsky/atlassian-api-client/compare/v5.0.0...HEAD)

## [5.0.0](https://github.com/dichovsky/atlassian-api-client/compare/v4.0.0...v5.0.0) (2026-11-10)

This major release fixes the core transport, error, auth and retry layers, covers the operations Atlassian added to the Jira platform v3 spec since its 2026-09-02 snapshot and to the Confluence v2 spec since its 2026-08-29 snapshot (both are re-pinned to 2026-11-08; the Jira Software snapshot is unchanged; experimental endpoints are marked as such in their JSDoc and may change upstream without notice), and corrects many SDK resources, `atlas` CLI actions, the bundled skill and the docs against the pinned specs. It includes breaking changes: new overloads and changed types that break subclasses, hand-typed fakes and code that reads the types back; CLI inputs that are now refused before sending; CLI output that now shows the server's response instead of a placeholder; flags and filters 4.0.0 accepted and ignored that now take effect; and stricter retry and redirect handling for writes. No package-root export is removed or renamed. Review the breaking changes and migration notes below before upgrading from 4.x.

### Breaking changes

**Core transport and errors**

- **Connect JWT signatures differ from 4.0.0** for any request whose path was absolute, carried a trailing slash, or contained `&`; for a `jwt` parameter passed through the query map; for a parameter present both in the path's query string and in the query map (the map value now replaces the path's, as on the wire); and for a repeated query parameter whose values percent-encode. The new values are the spec-correct ones. Every request signed by `createConnectJwtMiddleware` was affected, because resources emit absolute-URL paths — those signatures were rejected before and work now. Confluence Connect apps must additionally set `contextPath: '/wiki'`.
- **`HttpError.message` may differ.** Jira validation failures now name the offending fields, and a blank server message now yields the status default rather than an empty string. Recheck any code matching on exact message text.
- **`toJSON().headers` may carry more data than before.** `set-cookie` can now hold several joined values instead of one. That joined string is for logging and persistence, not re-parsing — a cookie's own `Expires` attribute contains a comma. Read `response.headers.getSetCookie()` for individual cookies, and redact or drop `set-cookie` before writing this projection to a log or store.
- **`toJSON().headers` is now a null-prototype object** (`Object.create(null)`), so a server header named `constructor` or `__proto__` can no longer collide with an inherited member or be dropped outright. The declared type is still `Record<string, string>` and `JSON.stringify` is unaffected, but `hasOwnProperty`, `toString`, and the other `Object.prototype` methods are not available on it, `console.log` prefixes it with `[Object: null prototype]`, and `assert.deepStrictEqual` / `toStrictEqual` against a plain object literal now fails. Use `Object.hasOwn(headers, name)` and `toEqual`.
- **A `tokenEndpoint` with a non-default port or embedded userinfo is rejected at construction time**, throwing `ValidationError` from `createOAuthRefreshMiddleware()`. There is no opt-out: `allowedTokenEndpointHosts` gates the host only and cannot re-permit a port. A self-hosted token gateway or local mock on an explicit port that worked in 4.0.0 will now fail to start; route it through the host's normal name and rely on DNS or a proxy.
- **The OAuth token endpoint must not redirect.** A self-hosted IdP or proxy that answered the refresh POST with a 3xx used to be followed. It now throws `OAuthError` with the 3xx status. Point `tokenEndpoint` at the final URL.
- **An out-of-range `maxClockSkewSeconds` throws per call, not at startup.** `AsymmetricJwtVerifyOptions` is a plain argument to `verifyConnectAsymmetricJwt()`, so there is no construction step to fail at: a bad value — `Number(process.env.JWT_SKEW)` yielding `NaN`, say — boots clean and passes health checks, then throws on the first inbound token, after signature verification succeeds. Validate the value yourself at boot if you source it from the environment.
- **`computeQsh()` throws `ValidationError` for an absolute-URL `path` that does not parse** (`computeQsh: path is not a valid absolute URL`; the value is not echoed). 4.0.0 hashed such a path as given. `createConnectJwtMiddleware` calls it with the request path, which resources build from the validated `baseUrl`, so this mostly affects direct callers.
- **Retry and `NetworkError` classification changed compared with 4.0.0.**
  - Client-side `fetch` argument errors now reach the caller as the raw `TypeError` that `fetch` threw: errors with no `cause`, or a `cause` with no system code (an invalid header, a bad method, a blocked port), and undici's `UND_ERR_INVALID_ARG`, `UND_ERR_NOT_SUPPORTED` and `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH`. They used to be a retried `NetworkError`. They are not retried, and the circuit breaker does not count them. If an `instanceof NetworkError` handler also covered those, catch `TypeError` as well.
  - A `TypeError` from `fetch` whose `cause` carries a system code that is not on the transient list is still a `NetworkError`, but it is no longer retried and `retryable` is `false` on it. 4.0.0 retried every `TypeError` that `fetch` threw. This covers TLS rejections (`CERT_*`, `ERR_TLS_*`, `ERR_SSL_*`, `EPROTO`, `SELF_SIGNED_CERT_IN_CHAIN`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`), a closed or destroyed undici dispatcher (`UND_ERR_CLOSED`, `UND_ERR_DESTROYED`), and local resource errors such as `EMFILE` and `ENOBUFS`. Still retried: `ECONNRESET`, `ECONNREFUSED`, `ECONNABORTED`, `EHOSTUNREACH`, `EHOSTDOWN`, `ENETUNREACH`, `ENETDOWN`, `ENOTFOUND`, `EAI_AGAIN`, `ETIMEDOUT`, `EPIPE`, `UND_ERR_SOCKET` and `UND_ERR_CONNECT_TIMEOUT`, and, for GET only, `UND_ERR_HEADERS_TIMEOUT` and the `UND_ERR_BODY_TIMEOUT` that undici raises while the response body is read (next bullet).
  - A socket failure while the client reads a 2xx response body (`TypeError: terminated` with cause `UND_ERR_SOCKET`, or undici's `UND_ERR_BODY_TIMEOUT`) is now a `NetworkError`, and the circuit breaker counts it. 4.0.0 let the raw `TypeError` escape for every method and never retried it. A GET is now retried. On POST, PUT, PATCH or DELETE the error has `retryable: false`: the write may have succeeded, so check server state before re-sending it. A `responseType: 'stream'` body is handed to you unread, so a failure while you read it is still the raw `TypeError`.
- **Redirects on writes are checked.** 4.0.0 let `fetch` follow every redirect for every method to any http or https host and port. When `fetch` itself refused a target (for example a `Location` that did not parse, another scheme such as `ftp:` or `data:`, a port `fetch` blocks such as 6000, or a URL with a username or password), the request failed as a `NetworkError` and was retried. Now a POST, PUT, PATCH or DELETE is sent with `redirect: 'manual'`. A redirect to a host outside `allowedHosts`, to a non-https scheme (such as plain `http://`), to a non-default port, to a URL with a username or password, or with an unparseable `Location` is refused, and nothing is sent to that target. A 303 (or a POST's 301/302) throws `HttpError` with the 3xx `status` and `requestId`. The server may have applied the write, so check its state before sending it again. A 307/308 (or a 301/302 on PUT, PATCH or DELETE) throws `ValidationError`, and nothing was applied. Neither is retried or counted by the circuit breaker. A loop of more than 20 redirects that keep the write's method (307/308, or a 301/302 on PUT, PATCH or DELETE) surfaces the last 3xx as an `HttpError`. After a 303 (or a POST's 301/302), `fetch` follows the GET's redirects itself, and more than 20 of them reject with `fetch`'s own `TypeError`, which is not retried. GET requests still follow redirects natively. A custom `config.fetch` must honour `RequestInit.redirect`.
- **Fewer write retries than 4.0.0.** A POST, PUT, PATCH or DELETE is no longer sent again in these cases, where the server may already have applied it. (1) Its response headers time out (`UND_ERR_HEADERS_TIMEOUT`): `NetworkError` with `retryable: false`. This happens only when the dispatcher's `headersTimeout` (300 s by default in Node's `fetch`) is shorter than `config.timeout` (default 30 s): a `config.timeout` above 300000, or a custom dispatcher with a shorter `headersTimeout`. Otherwise `config.timeout` fires first and throws `TimeoutError`, which neither version retries. (2) After a write's 303 (or a POST's 301/302), a transport failure on the follow-up GET is `NetworkError` with `retryable: false`, and so is any `NetworkError` a custom `config.fetch` throws there. (3) A 5xx or 429 on that GET is thrown without retry. Its class, status, body, `retryAfter` and `requestId` are unchanged. (4) A 401 on that GET under `createOAuthRefreshMiddleware` is rethrown without a token refresh. (5) Any other error on that GET is not retried, for example one a custom `config.fetch` throws, or `fetch`'s `TypeError` when that GET is redirected more than 20 times. In cases 1-3, 4.0.0 sent the write again up to `retries` more times (for case 3, when the status was 429, 500, 502, 503 or 504). In case 4 it refreshed the token and sent the write again once, even with `retries: 0`. In case 5 it sent the write again only when the error was a `TypeError` (the redirect-limit one included), carried a transient system code, or was a `RateLimitError` or retryable `HttpError`. Still as in 4.0.0: a write answered 500, 502, 503 or 504, or whose connection fails before any response (connection reset, socket closed), is retried, so the server may receive it more than once. A write the server itself answers 429 is retried, and a 401 under the OAuth middleware is refreshed and resent once. Cases 1-5 do not apply to a plain GET. The client records the not-retryable decision on the error object itself. If a custom `config.fetch` rejects that GET with one shared error instance that the client does not report as a `NetworkError` (a cached `HttpError`, say), later requests that reject with the same instance are not retried or token-refreshed either.
- **A `NetworkError` thrown by a custom `config.fetch` passes through as is for the request itself.** It is no longer wrapped in a second `NetworkError`, which 4.0.0 did when its `cause` chain carried a retryable system code. Its `retryable` flag now decides the retry. On the GET that follows a write's 303 (or a POST's 301/302), any `NetworkError` is instead rewrapped as `NetworkError` with `retryable: false`, with the original as `cause`.

**SDK, Jira**

Type-level changes (calls are unaffected unless stated):

- New members on exhaustive unions and client types. `AtlassianScope` gains 2 members, `read:bulk-job:jira` and `write:bulk-job:jira` (271 to 273). `JiraClient` gains the `agents` and `policies` resources (87 to 89) and 13 resource methods: the 9 on those two resources plus `fields.updateContextDefaultValues`, `forge.getBulkPinStatus`, `jql.getInvalidJqlAuditEntries` and `workflows.copyWorkflow`. On `ConfluenceClient`, the `pages`, `blogPosts`, `databases`, `folders` and `whiteboards` resources gain 42 methods (content permissions and database data). An exhaustive `Record<AtlassianScope, …>` or mapped type over these unions, and a hand-typed `JiraClient` or `ConfluenceClient` fake (or a full fake of one of those resources), no longer type-checks until it covers the new members.
- `issues.update(..., { returnIssue: true })` is now typed `Promise<Issue>`, not `Promise<void>`. This is a type-only break: code that passed a literal `returnIssue: true` and returns or stores that promise as `Promise<void>` no longer compiles, and neither does a subclass or hand-typed fake of `IssuesResource.update` (`JiraClient['issues']['update']`) that returns `Promise<void>`. Only a literal `true` (or an `as const` object) selects the `Promise<Issue>` type; a `boolean` variable or widened object such as `const p = { returnIssue: true }` stays typed `Promise<void>` although the issue is still resolved at runtime when the value is `true`. Calls without `returnIssue` are unchanged.
- `issues.deleteAllWorklogs()` and `issues.moveWorklog()` gain a `returnOutcome: true` overload typed `Promise<WorklogBulkOutcome>`. This is a type-only break: a subclass or hand-typed fake that implements either method as returning only `Promise<void>` (for example `const f: IssuesResource['deleteAllWorklogs'] = async () => {}`, or a `Pick<IssuesResource, 'moveWorklog'>` fake) no longer compiles. Only a literal `returnOutcome: true` (or an `as const` object) selects the `Promise<WorklogBulkOutcome>` type; a `boolean` variable or widened object stays typed `Promise<void>`, although the outcome is still resolved at runtime when the value is `true`. Plain calls, `Parameters<>` and `ReturnType<>` are unchanged.
- `setPropertyBulk` / `deletePropertyBulk` (`JiraClient['bulk']`) gain overloads. Calls are unaffected: the two-argument form and `{ returnTask: false }` stay `Promise<void>`, and `{ returnTask: true }` or a non-literal `BulkIssuePropertyOptions` give `Promise<JiraTask | undefined>`. Hand-typed fakes or implementations that annotate the return type no longer compile (TS2322). A `Promise<void>` annotation fails. So does `Promise<JiraTask | undefined>`, because it must also satisfy the `Promise<void>` overload. Subclass overrides fail with TS2416. `ReturnType<…>` / `Parameters<…>` of these methods now resolve from the last overload (`Promise<JiraTask | undefined>`, three parameters).
- `fields.delete` is now overloaded: `(fieldId, { returnTask: true }) => Promise<TaskProgressBeanObject | undefined>` plus `(fieldId, params?) => Promise<void>`. A hand-typed fake or implementation of `JiraClient['fields']['delete']` that returns `Promise<void>` no longer compiles (TS2322). Examples are a `Pick<JiraClient['fields'], 'delete'>` object or a subclass override reached through a deep import. Plain `fields.delete(fieldId)` calls are unchanged. A non-literal `DeleteFieldParams` argument selects the `Promise<void>` overload even when its `returnTask` is `true` at runtime; in that case the promise still resolves the task.
- `client.config.removeFieldParameters` is overloaded: `(body)` returns `Promise<void>` and `(body, { returnResults: true })` returns `Promise<RemoveFieldParametersResult | undefined>`. A fake or stub typed as `JiraClient['config']` (or a `Pick<>` of it) no longer type-checks (TS2322) if its `removeFieldParameters` is declared to return `Promise<void>`, for example `(): Promise<void> => ...`, `() => Promise.resolve()` or a class method. `async () => {}`, `async () => undefined`, `() => Promise.resolve(undefined)` and a `Promise<undefined>` return type still type-check. `ConfigResource` is not exported from the package root. A subclass of it imported through an internal path gets TS2416 and must declare both overloads.
- `issueSecuritySchemes.associateToProject` and `issueSecuritySchemes.removeLevel` are now overloaded, and a literal `{ returnTask: true }` selects a `Promise<TaskProgressBeanObject | undefined>` overload. A hand-typed fake of either method whose return type is annotated `Promise<void>` (for example a `Pick<JiraClient['issueSecuritySchemes'], 'associateToProject' | 'removeLevel'>` object) fails with TS2322, and a subclass override returning `Promise<void>` (`IssueSecuritySchemesResource` through a deep import) fails with TS2416. Plain calls without `returnTask` are unchanged and still resolve `void`. A non-literal options or params value whose `returnTask` is `true` at runtime is typed `Promise<void>` but resolves the task.
- The params overload of `projects.getProjectsFields` is now what `ReturnType`/`Parameters` infer. A subclass or hand-typed fake declared as `getProjectsFields(): Promise<unknown[]>` no longer compiles (TS2416, or TS2322 for `Pick<ProjectsResource, 'getProjectsFields'>` with `async () => []`). The equivalent fakes for `get`, `recent`, `listAllComponents` and `loadAvatar` still compile.
- `CreateProjectData.projectTypeKey` is optional. Passing it works as before, but code that reads it from a `CreateProjectData` as `string` now sees `string | undefined` under `strict`.
- `AssignableSearchParams.project` is now optional, and `fields.setContextIssueTypes` takes `AddIssueTypesToContextBody` (`issueTypeIds?: readonly string[] | null`) instead of `FieldContextIssueTypeIdsBody`. Code that reads these parameter types back, e.g. `p.project` as a `string` or `b.issueTypeIds.length`, no longer compiles without a guard. Callers that pass them are unaffected.
- `JqlQueryToSanitize.accountId` is widened from `string` to `string | null` (spec `nullable: true`). 4.0.0 already exposed it through the root-exported `SanitizeJqlQueriesData`. Writes are unaffected. Code that reads it back as `string | undefined`, e.g. `const a: string | undefined = data.queries[0]?.accountId`, gives TS2322.
- `CreateFilterData` / `UpdateFilterData` `sharePermissions` and `editPermissions` are widened from `AddFilterSharePermissionData[]` to `FilterSharePermissionWrite[]`. Writes are unaffected. Code that reads these arrays back as the flat type no longer compiles: reading `.groupname` gives TS2339, and assigning to `AddFilterSharePermissionData[]` gives TS2322.
- `SetDefaultResolutionData.id`, `AssociateSchemesToProjectsData.schemeId` and `OldToNewSecurityLevelMapping.oldLevelId` / `newLevelId` are now `string | null`. Code that reads them as `string` must handle `null` (TS18047). `SetDefaultResolutionData` and `OldToNewSecurityLevelMapping` are not exported from the package root, so for them this affects only code that derives them, for example through `Parameters<>`; `AssociateSchemesToProjectsData` is root-exported from 5.0.0.
- `priorities.setDefault` now types `data.id` as `string | null` (`SetDefaultPriorityData` is not root-exported, so callers that pass a string are unaffected). A hand-typed fake or subclass that reads `data.id` as a `string` (e.g. a `Pick<PrioritiesResource, 'setDefault'>` whose implementation calls `data.id.trim()`) fails with TS18047 ('data.id' is possibly 'null'). Code that derives the type through `Parameters<PrioritiesResource['setDefault']>[0]` and assigns `id` to a `string` fails with TS2322.
- `expression.evaluate` takes `ExpressionEvaluateData`. An object literal with `context.issues.jql.startAt` or `validation` no longer compiles; the endpoint rejects those keys. A variable typed `EvaluateExpressionData` is still accepted.
- `UpdatePriorityData.name` is now optional, and `DeletePriorityParams.replaceWith` is marked `@deprecated` (it is still sent when given).

Runtime changes:

- New `ValidationError`s before any request:
  - `issues.deleteAllRemoteLinks(key)` without `globalId`, and `issues.removeWatcher(key)` without `accountId`. Both sent a request Jira rejects with 400.
  - `statuses.bulkUpdate` rejects entries missing `id`, `name` or `statusCategory`, a value for any of them that is not a string (a numeric `id`, which 4.0.0 sent, now fails), and a `statusCategory` other than `TODO`, `IN_PROGRESS` or `DONE` (the spec `StatusUpdate` enum); the CLI `statuses bulk-update` fails the same way. `statuses.byNames`, `users.bulkGet` and `users.bulkGetEmails` reject empty lists. `issueComments.bulkFetch` rejects ids above `Number.MAX_SAFE_INTEGER`. `priorities.create` / `update` reject `iconUrl` together with `avatarId`. `priorities.update` with no fields throws `ValidationError`, and it no longer requires `name`.
  - `projects.getRole`, `addRoleActors`, `setRoleActors` and `deleteRoleActors` throw when the role ID is not a positive decimal integer. Decimal strings from untyped callers are still accepted.
  - `projects.loadAvatar` with a non-Blob body throws before any request; that overload stays `@deprecated`, so 4.0.0 code still type-checks. A Blob from another realm or a polyfill is copied into a native Blob, which costs one extra `arrayBuffer()` read.
  - `projects.getProjectsFields()` with no arguments throws; that overload is `@deprecated`.
  - `workflows.getTransitionRuleConfigs` with `draft: true` (or a non-boolean `draft`), and `updateTransitionRuleConfigs` / `deleteTransitionRuleConfigs` with a `workflowId.draft` other than `false`, throw without sending; `draft: false` is no longer sent. A non-object `workflows[]` entry (`null`, a number, a string, an array) also throws; 4.0.0 sent both to the server.
  - `fields.setContextIssueTypes` with neither `issueTypeIds` nor `isAnyIssueType` (`setContextIssueTypes requires at least one of issueTypeIds or isAnyIssueType`). 4.0.0 typed `issueTypeIds` as required but sent whatever body it was given.
  - `bulk.deletePropertyBulk` when the deprecated `filter` is combined with a defined top-level `entityIds` or `currentValue`. Top-level keys that are explicitly `undefined` count as absent.
  - `bulk.deletePropertyBulk` with an empty `entityIds`, at the top level or in the deprecated `filter`, and `bulk.setPropertyBulk` with an empty `filter.entityIds`. The spec does not say whether `[]` selects no issue or every issue. No signature changed.
- `applicationProperties.list({ key })` resolves a one-element array where 4.0.0 resolved the bare object, and `[]` for an empty body where 4.0.0 resolved `undefined`/`null`. Accordingly, `atlas jira application-properties list --key K` prints `[{…}]` instead of `{…}` (and `[]` when empty).
- `client.bulk.deletePropertyBulk(key, data)` now sends `entityIds` / `currentValue` at the top level of the DELETE body. 4.0.0 sent `{ filter: {...} }` as given. A 4.0.0-style `{ filter: {...} }` argument is now sent as the filter's criteria at the top level.
- `issueTypeScreenSchemes.listProjectAll({ query })` now filters; 4.0.0 yielded every project.
- `projects.recent({ maxResults })` and `atlas jira projects recent --max-results` no longer send `maxResults` (the field is `@deprecated`; the flag still parses and must be a positive integer). 4.0.0 sent it. Whether Jira honoured the undocumented param was not checked against a live site; if it did, `--max-results 5` now returns up to 20 projects.
- `search.searchAll` now sends `validateQuery`, `properties` and `fieldsByKeys` when they are given. A `validateQuery: 'strict'` caller can now get Jira's validation errors.
- `projectTemplate.createWithCustomTemplate` falls back to the followed task's `self` when there is no `Location` header. Under real fetch it used to resolve `undefined`.

**SDK, Confluence**

- Invalid likes-users limits throw a different message: `limit must be a non-negative integer, got: <n>` from `FooterCommentsResource.listLikeUsers`, `pages.listLikeUsers` and `blogPosts.listLikeUsers`; 4.0.0 said `limit must be a positive integer, got: <n>`. Negative, fractional, `NaN` and `Infinity` values are still rejected before any request; `limit: 0` is now sent (see Fixed).

For a negative, fractional or non-finite limit the class is still `ValidationError`, but the message changed from `limit must be a non-negative integer, got: <n>` to `limit must be a positive integer, got: <n>`. `FooterCommentsResource.listLikeUsersAll` behaves exactly as in 4.0.0.
- `TasksResource.listAll({ limit })` and `VersionsResource.listAllForPage(id, { limit })` throw `ValidationError` for a non-positive or non-integer limit before any request.
- Confluence labels list methods throw `ValidationError` for a `limit` that is not a positive integer.
- `comments.listFooter/listInline` put `status`/`resolution-status` in the request path as repeated params, and throw `ValidationError` for an invalid `limit`.
- `customContent.list()` / `listAll()` without `type` now throw `ValidationError`, and `atlas confluence custom-content list` requires `--type`. The spec marks `type` as required.
- `spaces.listProperties()` / `listPropertiesAll()` ignore `params.sort`, and `atlas confluence spaces list-properties --sort` is rejected.
- `ListSpaceRoleAssignmentsParams['role-type']` is widened from `SpaceRoleType` to `SpaceRoleType | (string & {})`. Calls are unaffected, but code that reads the property into a `SpaceRoleType` needs a narrowing.
- `ListCustomContentParams.id` and `ListCustomContentParams['space-id']` are widened from `string` to `string | readonly (string | number)[]` (spec `type: array`). Calls are unaffected, and a string is still sent as a single parameter. Code that reads either property back as a `string` no longer compiles: assigning it to `string | undefined` gives TS2322, and calling a string method such as `p.id?.split(',')` gives TS2339. Narrow it first, for example `typeof p.id === 'string'`.

**CLI, Jira**

Inputs now refused before any request is sent:

- `atlas jira users create` without `--products`. Under basic auth, `users create --email <addr>` fails and points to `--email-address`; bearer auth still accepts `--email`.
- `atlas jira issues update <key>` with neither `--summary` nor `--body` (4.0.0 returned `{ "updated": true }`), and `issues update --expand` without `--return-issue`.
- Empty `--summary`, `--resolution`, `--parent`, `--project` or `--type`, and a `--body` whose `update` or `transition` is not a JSON object, on `issues create|update|transition`. `issues transitions --transition-id ''`, and `issues create` with an empty-string `fields.project` / `fields.issuetype` in `--body` (Jira answers 400).
- `issues delete-all-remotelinks <key>` without `--global-id`, and `issues remove-watcher <key>` without `--account-id` (both sent a request Jira rejects with 400); to stop watching yourself pass your own account ID (`atlas jira users me`).
- `--adjust-estimate` values outside the spec enum (e.g. `move-worklog --adjust-estimate manual`).
- `atlas jira users viewissue-search` without `--issue-key` or `--project-key` (the spec requires one of them).
- `atlas jira bulk set-property` with both `--value` and `--expression`.
- `atlas jira configuration select-timetracking --url`, because the spec marks the provider `url` read-only. 4.0.0 sent it in the body.
- These flags had no effect and are now rejected with guidance: `--update-sequence-id` on `remote-link delete`, `flag delete`, `pipelines delete-build` / `delete-deployment`, and every `bulk-by-properties` action except `delete-devinfo` (4.0.0 accepted it and never sent it; the spec marks those guards deprecated and "no longer supported"); and `groups picker --user-name` (4.0.0 sent it and Jira ignored it; the spec says "no longer available").
- `atlas jira exists-by-properties get --entity-type` / `--entity-id`. 4.0.0 sent them as the property filters `entityType=…&entityId=…`; the same query is now `--properties entityType=<type>,entityId=<id>`. `exists-by-properties get` without `--properties` is also rejected, because Jira answers it with 400.
- App `--issue-id`, `--ids` and `--context-ids`, and every `--update-sequence-id`, must be positive decimal integers up to 2^53−1. Anything else (`0`, `0x10`, `1e3`, `10.0`, larger values) is rejected. An empty `--issue-id` / `--update-sequence-id` fails too. So does an app `--ids` / `--context-ids` that names no id (`''`, `','`), which used to send the request unfiltered. Other resources' `--ids` are unchanged.
- App field-context configuration filters that give `--project` without `--issue-type-id` (or the reverse), leave either one empty or blank, or combine more than one filter group; a `classification-levels list --status` that names no status (`''`, `','`); empty `bulk get-fields` / `get-transitions` cursors; `--properties` with a duplicate key, an empty key or value, or the reserved `_updateSequenceId` / `_updateSequenceNumber`; `groups picker` with both `--exclude-id` and an `--exclude` that names a group; `repository delete-entity` with an entity type other than `commit`, `branch` or `pull_request`.

### Fixed

**Core transport and errors**

- **Connect JWT QSH is canonicalized per the Connect spec.** `computeQsh()` now accepts an absolute URL as well as a path, strips the configured `contextPath`, removes a trailing slash, and escapes `&` in the path as `%26`. Resources emit absolute-URL paths, so signing previously hashed the scheme and host and produced a QSH the server rejected. A `jwt` parameter supplied through the query map is now excluded from the hash as well; a `jwt` already present in the path was excluded in 4.0.0.
- **Repeated QSH query values are sorted before encoding**, matching the reference `atlassian-jwt` implementation. Encoding first reordered values, because every percent-escape starts with `%` (0x25) and therefore sorts ahead of any character `encodeRfc3986` leaves literal.
- **An explicit query map now replaces a value already baked into the path**, as the wire does, instead of contributing a second occurrence of the parameter.
- **`maxClockSkewSeconds` is validated instead of silently trusted.** Non-number, non-finite, and negative values, and any value above one day (86,400), now throw `ValidationError` from `verifyConnectAsymmetricJwt()`. A millisecond value passed by mistake previously disabled expiry checking outright.
- **Responses whose `Headers` come from another realm are accepted.** The transport gated on `instanceof Headers`, which is realm-bound, so every successful response from the README's own `undici` `ProxyAgent` recipe failed with `Invalid ApiResponse structure`. The gate is now a duck-type check across the WHATWG `Headers` surface.
- **A socket failure while the response body is streaming is classified as `NetworkError`** instead of escaping as a raw `TypeError: terminated`, so the circuit breaker sees it. Unlike a reset before the headers, the server has already answered, so the request is retried only when it is a GET. A write the server already answered with a success has committed, and re-sending it would create a duplicate. Error responses keep their server-sent status, which remains authoritative.
- **Client-side `fetch` argument errors are no longer treated as network failures.** These requests would fail the same way on every retry: an invalid header value, a bad method, a header undici refuses to send, or a GET that `fetch` redirects to a target it refuses (a blocked port such as 6000, a non-HTTP(S) scheme, or a URL with a username or password). Only that redirected GET reached the network. The undici codes for the refused headers are `UND_ERR_NOT_SUPPORTED` for an `Expect` header, `UND_ERR_INVALID_ARG` for an `Upgrade` header, and `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH` for a `Content-Length` that disagrees with the body. These errors now reach the caller as a raw `TypeError`. They are not retried, and the circuit breaker does not count them. In 4.0.0 the breaker counted every attempt, so repeated calls with a bad header could open the circuit for healthy requests. Classification rests on the system code `fetch` attaches to `cause`. Any other `TypeError` that carries such a code is still a `NetworkError`, as in 4.0.0, and is retried only when the code is transient. The transient list gained `ECONNABORTED`, `EHOSTUNREACH`, `EHOSTDOWN`, `ENETUNREACH`, `ENETDOWN`, and `UND_ERR_HEADERS_TIMEOUT` and `UND_ERR_BODY_TIMEOUT` (both retried only for GET).
- **A write whose response headers time out is sent once.** A POST, PUT, PATCH or DELETE that fails with undici's `UND_ERR_HEADERS_TIMEOUT` is now a `NetworkError` with `retryable: false`. That code means the request was sent in full and no complete response headers had arrived, so the server may still be applying it. 4.0.0 retried it. A GET with a headers timeout is still retried. Connection-phase failures (`ECONNRESET`, `ECONNREFUSED`, `UND_ERR_SOCKET`, `UND_ERR_CONNECT_TIMEOUT` and the other connection codes in the transient list) keep the 4.0.0 retry policy for every method.
- **OAuth token refresh no longer follows redirects.** A 307/308 from the token endpoint replayed `client_secret` and `refresh_token` to whatever host `Location` named, past `allowedTokenEndpointHosts`. A 3xx now fails as `OAuthError` with that status.
- **Requests with a body no longer follow a redirect outside `allowedHosts`.** `fetch` replayed a 307/308 (or a 301/302 on a write other than POST) with its body to any host, port or scheme. Every non-GET request is now sent with `redirect: 'manual'`, and the transport follows a hop only when the target passes the same HTTPS, `allowedHosts` and default-port checks as the original URL and carries no username or password. A 303, or a 301/302 on POST, continues as a body-less GET, so Jira's documented 303-to-task responses keep working. GET requests still follow natively, because attachment downloads redirect to the media host.
- **A write whose redirect the client refuses is reported as possibly applied, and is not sent again.** Some POST, PUT, PATCH or DELETE requests are answered with a 303 (or, for a POST, a 301/302) whose `Location` the client will not follow: a host outside `allowedHosts`, a non-https scheme (such as plain `http://`), a non-default port, a URL with a username or password, or an unparseable URL. The client now throws `HttpError` with the 3xx `status`, the redirect's `requestId`, and the `ValidationError` as `cause`. Nothing is sent to that target and the request is not retried. The message says the server may already have applied the request. 4.0.0 let `fetch` follow such a redirect as a GET to any http or https host and port. When `fetch` itself refused the target (for example a `Location` that did not parse, another scheme such as `ftp:` or `data:`, a port `fetch` blocks such as 6000, or a URL with a username or password), the request failed as a `NetworkError` and the write was sent again.
- **A write is not sent again after the GET its redirect leads to fails.** When a POST, PUT, PATCH or DELETE is answered with a 303 (or a POST with a 301/302), the client follows with a GET. A failure on that GET no longer resends the write. A transport failure, or any `NetworkError` a custom `config.fetch` throws, becomes a `NetworkError` with `retryable: false` and the original as `cause`. A 5xx or 429 is thrown without retry, with its class, status, body, `retryAfter` and `requestId` unchanged. Under `createOAuthRefreshMiddleware`, a 401 is rethrown without a token refresh. Any other error on that GET is not retried, for example one a custom `config.fetch` throws, or the `TypeError` `fetch` rejects with when that GET is redirected more than 20 times. 4.0.0 sent the write again, up to `retries` more times, after a transport failure, a `NetworkError`, or a 429, 500, 502, 503 or 504 on that GET. After a 401 under the OAuth middleware it refreshed the token and sent the write again once, even with `retries: 0`. For any other error there it sent the write again only when the error was a `TypeError`, carried a transient system code, or was a `RateLimitError` or retryable `HttpError`. For example, Jira's async project delete answers 303 to a task URL, and in 4.0.0 a 503 from that URL sent the delete again.
- **Jira field-level `errors` are surfaced in error messages.** `ErrorCollection` bodies populate `errorMessages` and `errors` independently, and 400s from issue create, update, and transition carry the actionable detail in `errors` while `errorMessages` comes back empty — those failures previously degraded to a bare `HTTP error 400` naming no field. Both fields are now rendered, under the existing length cap.
- **A present-but-blank server message falls back to the status-derived default.** A body of `{"message": ""}` produced an error whose `.message` was the empty string, hiding even the HTTP status.
- **`toJSON()` keeps every `Set-Cookie` value.** `Headers.entries()` yields a separate entry per `Set-Cookie`, so a plain assignment kept only the last: a response setting a session cookie plus a CSRF cookie serialized with the session cookie missing. Duplicate names are joined with `', '`.
- **`detectRequiredScopes()` ignores inherited property names.** Passing `'constructor'`, `'toString'`, or `'__proto__'` returned an inherited non-array value and threw `scopes is not iterable`, breaking the documented contract that unknown operation names are ignored.
- **The OAuth token endpoint rejects a non-default port and embedded userinfo.** The check was hostname-only, so `https://auth.atlassian.com:8443/oauth/token` passed with the default allowlist and shipped the `refresh_token` and `client_secret` to whatever listens there. This path is now at least as strict as the tenant-API path, which already rejected both.
- **Trailing-slash trimming of `baseUrl` and `contextPath` is linear.** The previous `/\/+$/` replace was quadratic on a long run of slashes (CodeQL `js/polynomial-redos`; about 12 s at 80,000 characters).
- **Path sanitizing for logging is linear.** `sanitizePathForLogging` runs on every request. It redacted JWT-shaped text with a regex that was quadratic on a long run of `eyJ` (about 8.5 s for 120,000 characters). Its fallback query strip for an unparseable path was quadratic on a long run of `?` that ends in a line break. Both are now linear scans, and the output is byte-identical.
- A fetch that rejects with a non-Error value now gives `NetworkError` the message `Network request failed` instead of an empty string.

### Migration

Each item pairs with a bullet under **Breaking changes**.

**Core transport and errors**

- Confluence Connect apps: set `contextPath: '/wiki'` in the `createConnectJwtMiddleware` config. Apps that call `transport.request()` directly with `createConnectJwtMiddleware` must pass an absolute URL as `path`. A relative path is hashed as-is and Atlassian rejects it with a 401.
- If you catch `NetworkError` for 'cannot reach Atlassian', no change is needed: unreachable-host, network-down, undici timeouts and TLS failures are still `NetworkError`, as in 4.0.0, but only the transient codes are retried. If you relied on the automatic retry of another coded failure, such as `EMFILE`, retry it yourself. Also catch raw `TypeError` if you relied on argument errors (an invalid header value) arriving as `NetworkError`, as they did in 4.0.0.
- If you caught `TypeError` (`terminated`) for a 2xx response body cut off mid-read, catch `NetworkError` instead. A GET is retried before the error reaches you. On a write, `retryable` is `false`.
- If you build `NetworkError` in custom middleware and do not want it retried, pass `{ retryable: false }`.
- If you resend writes yourself after a `NetworkError`, check `retryable` first. `false` means the server may have applied the write, so check its state before sending it again.
- A write whose redirect the client refuses now fails instead of being followed. A 303 (or a POST's 301/302) throws `HttpError` with the 3xx status and `requestId`. The server may have applied it, so check state before resending. A 307/308 (or a 301/302 on PUT/PATCH/DELETE) throws `ValidationError`, and nothing was applied. If the redirect target is a host you trust, add it to `allowedHosts` (the client then sends the request's `Authorization` header there too); it must also be `https://` on the default port, with no username or password in the URL.
- If you set `config.timeout` above 300000 for slow writes, a write that gets no response headers within the dispatcher's `headersTimeout` (300 s by default) now fails once with `NetworkError` (`retryable: false`) instead of being sent again. To wait for the full `timeout`, give `fetch` a dispatcher whose `headersTimeout` is at least `config.timeout`.
- OAuth: point `tokenEndpoint` at the final URL, on the default port and without userinfo. Route a self-hosted token gateway or local mock through the host's normal name.
- If you source `maxClockSkewSeconds` from the environment, validate it at boot. Recheck code that matches exact `HttpError.message` text. Compare `toJSON().headers` with `toEqual` and `Object.hasOwn`, read cookies with `response.headers.getSetCookie()`, and redact `set-cookie` before logging the projection.

## 1.0.0 (2026-05-21)

### Added

- **oauth (B016)** — `OAuthRefreshConfig.retryJitterMs?: number` (default `100`) and `OAuthRefreshConfig.failureCooldownMs?: number` (default `1000`) protect `createOAuthRefreshMiddleware` against two herd patterns that previously slipped through the single in-flight refresh dedup. `retryJitterMs` spreads concurrent post-refresh retries across `[0, retryJitterMs)` so N waiters no longer dispatch their retried API calls in the same microtask the moment the shared refresh resolves — flattening the burst that could re-trigger upstream rate-limits or push a just-recovered backend back over capacity. `failureCooldownMs` caches the most recent refresh **failure** for the configured duration and replays it without re-firing the token endpoint, so an auth-server outage no longer drives one refresh attempt per incoming 401 (previous behaviour was an unbounded loop). Concurrent waiters at the moment of failure already shared one rejection; the cooldown protects the _next_ wave. Both knobs accept `0` to disable for callers who need the prior behaviour, and are validated as non-negative finite numbers at `createOAuthRefreshMiddleware` construction (`ValidationError` otherwise). The cooldown replays the original refresh error (typically `OAuthError`) so the root cause is preserved. The jitter sleep honours `RequestOptions.signal` — aborting a caller during the sleep rejects with `signal.reason` immediately and clears the pending timer.
- **transport (B026)** — `ClientConfig.maxResponseBytes?: number` caps the size of any single buffered response body the transport will materialise. When set, the transport throws the new `ResponseTooLargeError` (extends `AtlassianError`, code `RESPONSE_TOO_LARGE_ERROR`) instead of loading an oversized body into memory. Applies to `responseType: 'json'` and `'arrayBuffer'` on the success path AND to the error-response body parsed for error-message extraction — so a hostile or misconfigured upstream returning a multi-gigabyte 5xx body cannot exhaust the Node heap on a single request. `responseType: 'stream'` is exempt by design (caller owns drain/abort). Detection is twofold: a fast-fail on `content-length` when the header is present and exceeds the cap (no body bytes are read), plus a running stream-read tally that aborts mid-read via `reader.cancel()` when the byte total crosses the cap — handles chunked transfers, missing headers, and servers that lie about `content-length`. Default is `undefined` (no cap, preserves prior behaviour); recommended for any client consuming responses from a third-party or untrusted proxy. Must be a finite positive integer when supplied; rejected at `resolveConfig` time otherwise.
- **errors (B026)** — `ResponseTooLargeError` exported from `src/core/index.ts`. Carries `limitBytes` (the configured cap that was exceeded) and `status` (the HTTP status of the response whose body overflowed — populated by the transport on both the success and error paths so callers can classify the originating response). Not an `HttpError` — it preempts the would-be `HttpError` on the error path rather than being one.

### Breaking

- **oauth (B036)** — `createOAuthRefreshMiddleware` (and direct `fetchRefreshedTokens` callers) now throws `ValidationError` at construction time when `OAuthRefreshConfig.tokenEndpoint` resolves to a host other than `auth.atlassian.com`. Integrations that previously passed a custom `tokenEndpoint` (self-hosted IdP, proxied auth, staging) must opt in by also setting `OAuthRefreshConfig.allowedTokenEndpointHosts: readonly string[]` — the list REPLACES the default, mirroring `ClientConfig.allowedHosts` semantics. Migration: pass `allowedTokenEndpointHosts: ['<your-host>']` alongside the existing `tokenEndpoint`. The error message names the field, so existing code fails fast with an actionable diagnostic rather than silently leaking credentials. See `### Security` below for full rationale.

### Security

- **transport (B035)** — `sanitizePathForLogging` (the debug-log path sanitiser invoked once per request inside `HttpTransport.executeFetch`) now redacts a substantially wider set of credential markers and credential-shaped values. Segment-name markers grew from `{token, key, secret, auth}` to also include `password`, `pwd`, `apikey`, `api_key`, `access_token`, `refresh_token`, `bearer`, `jwt`, `assertion`, `client_secret`, `signature`, `sig`, `jsessionid`, `sid`, `session` — the next path segment after any of these (whole-segment, case-insensitive) is replaced with `***`. The same expanded set drives the `name=VALUE` marker regex, which now matches anywhere inside a segment and is terminated by `/&;?#` so matrix params (`;jsessionid=ABC`) are scrubbed alongside query-style markers smuggled into the path. A new JWT compact-serialisation regex (`eyJ[base64url].[base64url].[base64url]`) catches bearer JWTs accidentally embedded directly in a path with no preceding marker — replaced with `***.jwt.***`. The fallback branch (used when `new URL(...)` throws on malformed input) now strips `//user:pass@host` userinfo before redaction, closing a leak that previously echoed broken URLs with embedded credentials verbatim. Excluded by design (false-positive risk): `code`, `state`, `xdm_e`, `lic`, `cp` — Jira issue keys like `/issue/AC-1` and Atlassian Connect query params (already covered by the query-strip step) remain unchanged. No public API change; the redactor is internal to debug logging.
- **oauth (B036)** — `OAuthRefreshConfig.tokenEndpoint` is now validated against a host allowlist at `createOAuthRefreshMiddleware` construction time (and re-asserted inside `fetchRefreshedTokens` for direct callers). The default allowlist is `['auth.atlassian.com']` — the documented Atlassian Cloud OAuth 2.0 3LO token endpoint host, matching the default `tokenEndpoint`. Self-hosted IdPs, proxied auth, and staging endpoints must opt in via the new `OAuthRefreshConfig.allowedTokenEndpointHosts?: readonly string[]` field, which REPLACES (not augments) the default — mirroring `ClientConfig.allowedHosts` semantics. A misconfigured `tokenEndpoint` (typo, poisoned env var, social-engineered config PR) now throws `ValidationError` fail-fast at startup instead of POSTing `client_id` + `client_secret` + `refresh_token` to an attacker host on the very first 401. Defence-in-depth pair to the existing transport-side allowlist (B034); the OAuth refresh path is on a separate code path that bypasses `ClientConfig.allowedHosts` by design.

### Added

- **retry** — `executeWithRetry<T>(operation, config, signal?)` exported from `src/core/index.ts` runs any async operation under the same retry semantics as `HttpTransport` (exponential backoff with jitter, server-advertised `retry-after` honoured for `RateLimitError`, abort-aware between-attempts sleep). Useful for custom `Transport` implementations that want to reuse the retry policy. `RetryConfig` interface also exported.
- **middleware** — `createMiddlewareChain(middlewares, terminal)` exported from `src/core/index.ts` composes a middleware chain with outermost-first semantics (matches `HttpTransport`'s internal composition). Empty middleware array returns the terminal handler unchanged.
- **codemap** — `CODEMAP.md` machine-readable symbol index is generated by `scripts/generate-codemap.js` and committed at repo root. Captures the transitively-resolved public API surface, per-file symbol locations with line numbers, JSDoc summaries (with `@deprecated`/`@example`/`@since` preserved), and class member layouts. `npm run codemap` regenerates; `npm run codemap:check` (wired into `validate`) fails CI if the committed file drifts from source. Output is byte-identical across reruns, with staleness detected via `sourceHash` over sorted file paths + contents.
- **pagination** — `PaginateOptions { maxPages?, logger? }` parameter on `paginateCursor`, `paginateOffset`, `paginateSearch`. `maxPages` (default 10000) caps the number of pages requested and emits a single `warn` once the page count crosses 80% of the limit, making runaway iteration observable before it terminates. `paginateCursor` additionally throws the new `PaginationError` when the server returns the same cursor on consecutive responses, preventing infinite-loop failure modes from an upstream regression. The legacy positional `Logger` argument on `paginateCursor` is still accepted for backwards compatibility.
- **errors** — `PaginationError` (extends `AtlassianError`, code `PAGINATION_ERROR`) exported from `src/core/index.ts` for callers that want to catch pagination-specific failures distinctly from validation or transport errors.

### Fixed

- **cli (B031)** — `atlas --version` now reports the real package version read from `package.json` instead of the hardcoded `0.1.0` literal that had drifted six minor releases out of date (the published package was `0.7.0` while the CLI still printed `atlas v0.1.0`). Version resolution is centralised in a new `src/cli/version.ts` module exporting `resolvePackageVersion(moduleUrl, fs?)` and `VersionResolutionError`; the CLI entry and the `install-skill` command both consume it, so the skill-frontmatter stamp and the `--version` flag can no longer disagree. The CLI entry was also factored into a reusable `runCli(argv, stdout, stderr, resolveVersion?)` export with a stable bin-vs-import guard (matches `import.meta.url` against the entry script's `realpath`) so tests can assert the version output without spawning a subprocess. Output format is unchanged (`atlas v<version>`); behaviour on missing/invalid `package.json` is unchanged for `install-skill` (still throws `InstallSkillError` with exit code 1) and now produces an equivalent failure mode for the CLI entry's `--version` path.
- **pagination (B037)** — `paginateOffset` and `paginateSearch` no longer trust the server-echoed `maxResults` for cursor advancement or short-page detection. Advancement now uses `values.length` (rows actually delivered), and short-page detection uses `Math.min(pageSize, serverMaxResults ?? pageSize)`. This fixes two silent data-loss / duplication scenarios: (1) when Jira clamps `maxResults` below the requested `pageSize`, the old advancement (`startAt += response.maxResults`) over-advanced and skipped rows; (2) when the server echoed a `maxResults` larger than the caller's `pageSize`, the same code path skipped rows on the next request. A new forward-progress guard throws `PaginationError` when the server returns an empty page mid-iteration while `total` (or `isLast === false`) still indicates more data — previously this silently truncated the result set. Public API and existing terminal conditions (`isLast === true`, `total` exhausted, true short page) are unchanged.

## 0.6.0 (2026-04-20)

### Added

- **transport** — `ApiResponse<T>` now exposes a `rateLimit?: RateLimitInfo` field populated from `x-ratelimit-*` response headers on every successful request. When `nearLimit === true` the configured `logger` emits a `warn` so callers can proactively slow down before a 429.
- **transport** — `RequestOptions.signal?: AbortSignal` lets callers cancel in-flight requests (e.g. React `useEffect` cleanup, CLI SIGINT). The caller signal is composed with the internal timeout signal via `AbortSignal.any`; external aborts surface as `AbortError` while timeouts still throw `TimeoutError`.
- **cli** — `--auth-type basic|bearer` flag (and `ATLASSIAN_AUTH_TYPE` env var) so the `atlas` CLI can call Atlassian APIs with an OAuth/PAT bearer token. `--email` is not required when `bearer` is selected; `--token` is still required. Unknown values fall back to `basic` to preserve the historical default for existing invocations.

### Changed

- **transport** — 429 `Retry-After` delays now receive `0..retryDelay` jitter on top of the server-advertised floor. If `maxRetryDelay` leaves headroom above that floor, only the added jitter is capped to stay within that headroom. Prevents synchronized retry stampedes from clients that share a rate-limit bucket.
- **transport** — the retry loop now wraps the middleware chain (previously middleware wrapped retry). Errors thrown from middleware — including `OAuthError` with a 5xx refresh status — are now eligible for the standard retry/backoff path.
- **oauth** — `OAuthError` now extends `HttpError` (previously `AtlassianError`) and sets `status = refreshStatus ?? 0`. Transient token-endpoint failures (5xx) are retried automatically via `shouldRetry`; 4xx stay fatal. Public error `code` remains `'OAUTH_ERROR'`.
- **pagination** — offset paginators (`paginateOffset`, `paginateSearch`) now terminate when the server returns a short page (`values.length < maxResults` / `issues.length < maxResults`), even if `isLast` and `total` are absent from the response. Prevents infinite loops against servers that clamp page size without populating those fields.

### Fixed

- **transport** — `request<T>()` now validates the shape of the response produced by the middleware chain before exposing it as `ApiResponse<T>`, throwing `ValidationError` on null, primitives, or objects missing `data`/`status`/`headers` (or with non-numeric `status` or non-`Headers` headers). A misbehaving middleware can no longer return a malformed value that crashes downstream consumers.
- **transport** — logged request paths are now passed through `sanitizePathForLogging`, which strips query/fragment parts and redacts path segments following sensitive markers (`token`, `key`, `secret`, `auth`). Applies to debug and near-limit warn logging. URL parsing is wrapped in a try/catch so a malformed input falls back to a best-effort pathname rather than crashing the request.
- **errors** — `extractErrorMessage` now filters non-string entries out of Jira-style `errorMessages` arrays before joining, so objects or `null` in the array no longer leak as `[object Object]` or `"null"` into error messages.
- **package** — removed dead `test:exports` script whose target file had been deleted in an earlier commit.

## 0.5.0 (2026-04-16)

### Fixed

- **transport** — `HttpTransport` previously held two distinct `baseUrl` values: `config.baseUrl` (the raw instance URL) and a separate constructor parameter (the API-specific URL).
