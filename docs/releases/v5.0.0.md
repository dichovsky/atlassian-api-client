# Release record: v5.0.0

This record covers the release of `atlassian-api-client` 5.0.0 from the last published version, 4.0.0. It holds the evidence gathered before the tag, plus links to the [parity matrix](v5.0.0-parity-matrix.md) and the [findings ledger](v5.0.0-findings.md). The evidence from publication and registry verification is added in a follow-up pull request after the `Publish` workflow finishes. Nothing here contains credentials.

## Versions

- **Previous published version:** 4.0.0. It is npm `latest`, its `gitHead` is `72d2d1604054c4580a86b31b6ee983a5d0d1a58e`, and that commit is the annotated tag `v4.0.0`. Its integrity is `sha512-FVHSR7eD2Fo2LwgAppu5P/HFG3QN8sUtbqyFzAkXEjj/ds9jJMblmECxVkueiAgYWYyhHRxf1ZJ4FrG4IeyNQg==`.
- **New version:** 5.0.0 (major). Before the release pull request, `package.json` read 4.1.0 from the never-tagged, never-published 4.1.0 preparation (#359). No `v4.1.*` or `v5.*` tag exists, and npm has no 4.1.0 or 5.0.0.
- **Why major:** the work was first planned as 4.1.0. Assembling the full delta showed changes of the kinds that the project's own 4.0.0 notes list under _Breaking changes_:
  - filters and flags that 4.0.0 accepted and ignored now take effect (for example `pages delete --draft` now deletes the draft instead of the published page);
  - inputs are now refused before any request;
  - CLI output shows the server's response instead of a placeholder;
  - `applicationProperties.list({ key })` returns an array;
  - new overloads and narrowed or widened types break subclasses and hand-typed fakes.

  The maintainer chose 5.0.0 on 2026-11-09. The full inventory is the _Breaking changes_ section of the 5.0.0 entry in [`CHANGELOG.md`](../../CHANGELOG.md).

## How the release was checked

1. **Baseline gate on the first candidate (`12a7562`):**
   - `npm ci` and `npm run validate` exit 0: 174 files, 13096 tests, 100% statements/branches/functions/lines.
   - `npm run api-coverage` exit 0.
2. **Audit of that candidate.** Parallel specialists covered SDK contracts and exports; transport, security and performance; new-operation wire shapes; CLI write semantics; test quality; docs; release notes; the release process; and the skill and help. A full API–CLI–skill sweep covered all 1115 public resource methods. It produced 351 findings: 1 CRITICAL, 56 HIGH, 138 MEDIUM and 156 LOW. A sample was adversarially re-verified (71 of 73 confirmed).
3. **Fixing.** Every finding went to a fenced work unit. For each one, the implementer reproduced it with a failing test, made the minimal fix, and proved the test passed. A separate fresh Opus reviewer then re-checked every disposition against the pinned specs before merge. Review rounds continued until the reviewer approved.
4. **Parity matrix verification, twice.** It was fully re-verified on the code of `0db5030` (#387 on `main`; the run used a local merge of #387 whose `src/`, `skill/`, `test/` and `spec/` trees are identical to `0db5030`): 59 gaps, closed by wave 4b. It was then refreshed on the final tree `11fb436`: 0 gaps (see below).
5. **Findings ledger.** On the final tree, every finding whose recorded disposition was not a plain FIXED was re-checked by an independent verifier. The one blocker found (the release notes did not list flags that 4.0.0 ignored and that now take effect) and five wording items were fixed in the release pull request.

## Release controls

These were read back from the GitHub API on 2026-11-10:

- **`main` ruleset (15061929):**
  - deletion and non-fast-forward blocked;
  - the aggregate `CI` status check required;
  - pull request required, with review threads resolved before merge (0 required approvals; the independent-reviewer rule is a repository process, recorded on each PR);
  - no bypass actors.
- **Tag rulesets:**
  - `release-tags-creation` restricts tag creation to repository admins;
  - `release-tags-immutable` blocks deletion, updates and force pushes of every tag, with no bypass.
  - A personal-account repository cannot enforce a tag-name pattern by ruleset (the API answers 422), so the `Publish` preflight enforces `vX.Y.Z`.
- **`release` environment:** required reviewer `dichovsky`; deployments only from tags matching `v*`.
- **Repository security:**
  - immutable releases are on;
  - secret scanning and push protection are on;
  - Dependabot security updates are on;
  - private vulnerability reporting is on;
  - CodeQL default setup covers actions, JavaScript/TypeScript and Python;
  - Actions must be pinned to full commit SHAs.
- **Tag signing:**
  - one SSH signing key (id 1314818) is registered for `dichovsky`;
  - repository-local Git config signs with `~/.ssh/id_rsa.pub` and an allowed-signers file;
  - a local rehearsal tag in a scratch repository passed `git verify-tag` (Good "git" signature for magdich.igor@gmail.com with RSA key `SHA256:hdA6eblLnP9IFSnr18Z2SpT58M6xaecuS+Hg6oEXaRI`);
  - GitHub-side verification of a signature from this key is checked on the release pull request's own signed commit;

- **npm trusted publishing:**
  - the maintainer reports that the trusted publisher is configured and working;

  - an agent cannot read the npm-side configuration.

## Runbook audit

`docs/RELEASING.md` was checked against `.github/workflows/publish.yml` and `ci.yml` (hardened in #372).

- **Preflight** checks that:
  - the tag matches `package.json`, the lockfile and the changelog heading;
  - it is an annotated tag whose GitHub verification is `verified`, resolving to a commit that is the exact `origin/main` tip;
  - a successful, completed `ci.yml` push run exists for that SHA.
- **Publish job:**
  - runs in the `release` environment and rechecks the `main` tip after approval;
  - requires npm trusted-publishing support;
  - builds, then publishes with `npm publish --provenance` over short-lived OIDC (`id-token: write`). No `NPM_TOKEN` is used.
- **Verify job:**
  - waits for the exact version on the registry;
  - smoke-tests a clean install, including the CLI version and skill version stamping;
  - requires SLSA v1 provenance naming this repository, workflow and tag.

The publish workflow does not create the GitHub release; the runbook covers that as a post-release step.
